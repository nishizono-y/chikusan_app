# grasp-skill-create

`grasp-*` Skill を作成・編集するときのルールを定義した Skill です。

---

## 1. いつ grasp-* Skill を作るか

ユーザーが次のいずれかを求めているとき:

- コードベースの構造・責務・依存関係を「把握したい」
- 設計方針やトレードオフを将来の自分や他者に伝えたい
- 用語定義・状態遷移など、コードを読んだだけでは分かりにくい意図を残したい

逆に「何かを生成・実行する」系（コード生成、テスト実行、デプロイなど）は grasp-* ではなく別のプレフィックスを使う。

---

## 2. 命名規則

| 種類 | プレフィックス例 | 目的 |
|---|---|---|
| 理解・把握 | `grasp-architecture`, `grasp-dataflow`, `grasp-dependency` | 既存の仕組みを読み解く |
| 生成・実行 | `glab-*`, `tdd-*`, `gen-*` | 何かを作る・動かす |

**ルール:** システム把握・構造整理を目的とする Skill には必ず `grasp-` プレフィックスをつける。

---

## 3. 記述方針（skill-writing-policy）

### 書くべきこと（変わりにくい・価値が高い）

- **設計方針とトレードオフ** — なぜこの構造になったか、別の選択肢との比較
- **責務分担と依存方向** — どのレイヤーが何を担い、どの方向に依存しているか
- **用語と状態遷移** — ドメイン固有の言葉の定義、状態の遷移ルール
- **意思決定の経緯** — 過去に検討して却下したアプローチとその理由

### 書いてはいけないこと（腐敗しやすい・コードを見れば分かる）

- 関数名・メソッドシグネチャ
- 行番号・個別ファイルパス
- 型定義・コード断片
- 実行手順のステップ（README や Makefile に書くべき内容）

### 核心の原則

> **「コードを読めば分かることは書かない」**
>
> Skill の価値は設計意図・責務の根拠・トレードオフを文語で残すことにある。
> コードは「何をするか」を語る。Skill は「なぜそうなっているか」を語る。

## 4. SKILL.md の構成テンプレート

```markdown
---
name: grasp-<対象>
description: >
  <いつトリガーするかを具体的に記述>
---

# grasp-<対象>

## 全体像
<このシステム/モジュールが何を解決しているか、一段上の視点で>

## 責務の分担
<誰が何を担うか。境界線とその理由>

## 依存方向
<何が何に依存しているか。循環依存を避けた理由など>

## 重要な設計判断
<なぜこのアーキテクチャか。検討した代替案と却下理由>

## 用語定義
<ドメイン固有の言葉の意味>

## 注意点・落とし穴
<コードを読むだけでは気づきにくい制約や暗黙の前提>
```

---

## 5. 品質チェックリスト

作成後、以下を確認すること:

- [ ] コードを見れば分かる情報（関数名・行番号など）が含まれていないか
- [ ] 「なぜ」が説明されているか（「何を」だけになっていないか）
- [ ] 1年後に読んでも意味が通じるか（実装詳細に依存していないか）
- [ ] プレフィックスが `grasp-` になっているか
- [ ] description に「いつトリガーするか」が具体的に書かれているか
