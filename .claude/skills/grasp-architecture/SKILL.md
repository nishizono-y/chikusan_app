# grasp-architecture

## 全体像

畜産農家の日次記録・出荷記録を管理する Web アプリ。
2 つのドメイン（日次記録・出荷記録）を独立した CRUD として提供し、
画面遷移の一部を Turbo Stream で差分更新することで UX を高める設計。

---

## 責務の分担

| レイヤー | 担うこと |
|---|---|
| **モデル** | ドメインルールのバリデーション。DB との入出力のみ。ビジネスロジックはまだ少ない |
| **コントローラ** | HTTP リクエストの受付・レスポンス形式の振り分け（HTML / Turbo Stream / JSON） |
| **ビュー（ERB）** | 画面の描画。Turbo Frame / Stream のテンプレートを含む |
| **JavaScript** | Hotwire（Turbo + Stimulus）の読み込みのみ。独自ロジックはほぼない |

モデルが太らないよう、バリデーションはモデルに集約し、コントローラは薄く保つ方針。

---

## 依存方向

```
ブラウザ
  └─ コントローラ（HTTPを受ける）
       ├─ モデル（DB操作・バリデーション）
       └─ ビュー（HTMLレンダリング）
            └─ Turbo（差分更新・ページ遷移）
```

JavaScript（Turbo）はビューが返す HTML に自動的に反応する設計で、
コントローラや Ruby 側のコードと直接結合していない。

---

## 重要な設計判断

### Turbo Stream は「削除」にだけ使っている
作成・更新はリダイレクト（フルページ）、削除だけ Turbo Stream で DOM を差分更新している。
理由は、削除は一覧ページからインラインで行われることが多く、ページ遷移なしで該当行を消すのが自然なUXだから。
作成・更新はリダイレクト後に flash メッセージを見せる用途が主のため、フルページで十分と判断。

### respond_to でフォーマットを明示的に切り分け
`format.turbo_stream` / `format.html` / `format.json` を各アクションで明示している。
Turbo Stream レスポンスを意図せず返さないよう、フォーマットの優先順位を制御するため。

### モデル間にアソシエーションはない
`DailyRecord` と `Shipment` は現時点で完全に独立。
同じ日付のデータを紐づけるユースケースが出てきた段階で関係を設計する想定（YAGNI）。

### Stimulus は最小限
現時点では Stimulus コントローラは `hello_controller.js`（デフォルト）のみで実質未使用。
Turbo で解決できないインタラクションが出てきたときに追加する方針。

## 用語定義

| 用語 | 意味 |
|---|---|
| **日次記録（DailyRecord）** | その日の死亡頭数・飼料使用量・飼料在庫・ワクチン接種・メモを記録するエントリ |
| **出荷記録（Shipment）** | 出荷日・頭数・平均体重・出荷先を記録するエントリ |
| **Turbo Stream** | サーバーから返された HTML の断片で DOM を差分更新する Hotwire の仕組み |
| **Turbo Drive** | リンク遷移・フォーム送信を AJAX に置き換えてページ全体を高速遷移させる仕組み（デフォルト有効） |

---

## 注意点・落とし穴

- **削除後のフラッシュ表示は Turbo Stream で独自実装している**
  通常の `redirect_to ... notice:` はフルページ遷移前提のため、Turbo Stream 削除時には flash が表示されない。
  `destroy.turbo_stream.erb` の中で flash 要素を差し込む処理を入れている。

- **JSON レスポンスはテスト・API 想定で残しているが現状未使用**
  `format.json` は scaffold 生成時のデフォルトで残っている。フロントエンドから叩く予定は現状ない。

- **ルートは `daily_records#index` がトップ**
  `/` にアクセスすると日次記録の一覧が表示される。出荷記録はナビゲーション等から辿る想定。
